# 执行 session 的事件回报

CEO、客户端管家、项目管家派工确认后结束管理轮次；空闲等待没有常驻模型。普通 topic 执行复用已有 coordination work/report/outbox/inbox，在原来源 session 可靠排队审阅。完成、失败、受阻和必要检查点才产生模型审查成本，不承诺 token 节省比例。网页关闭不影响客户端持久队列。普通执行者保持执行自主性，不强制递归派生。

按2026-11-13用户调整，预计5步以内能完成的工作由管理者直接做，超过5步才派工；需要派工时继续按 topic 复用执行 session，并沿用以下事件回报流程。步数按实际工作估计，不按工具调用次数计，也不把复杂工程合为一步；途中超出5步时带上已完成动作接续派工。执行者忙碌时不并行接手。该界限只适用于管理角色，不改变普通执行者的自主性或用户授权边界。

## 路由与持久投递

`start_web_session` 保留原 topic→client/project/session/task 映射，通过 `/api/agent/coordination` 的 subscribe 操作接入既有 WorkRoute，取得真实 workId/replyHandle，不创建第二套通知系统。服务端强制使用认证来源设备，核实管理 scope、账号、原普通项目和直接父子关系；子会话验证只分页读取元数据。路由包含 topic、来源链及订阅阶段，不接受伪造父上下文或兄弟会话。

执行端 watch 把当前轮接入既有 `coordination_work`/`coordination_pending`。后续普通续办在持久接受任务的同一事务中登记 outbox，丢失确认或 MCP 退出不会漏掉新轮次。完成/失败从现有持久 task_queue 与捕获的最终输出生成有界 WorkReport，不转发运行日志。失败、取消、停机中断可回填失败状态；未捕获结果不宣称成功。

事件含 ID、workId、topic、来源 client/project/session、taskId、event/status、complete、taskStatus、captured、时间、证据及过期标记，沿已有来源链回报。默认终态摘要最多6000字节；检查点摘要最多1800字节，最多4条各512字节证据。普通最终输出仍保留原执行页供按需核对，不复制完整历史。

事件触发本地 worker，30秒恢复定时器只重试待投递 outbox/订阅和修复丢失唤醒信号，不对运行中的普通 session 高频查询，不运行模型等待。账号认证由既有控制连接/HTTP接口复核；目标或来源离线时保留 outbox，断线恢复后重试。重启保留源管理映射、work 路由、pending、inbox 与原任务/会话数据。

源管理端在同一事务中追加结构化结果卡和去重 inbox；事件 ID 对应稳定的内部审阅任务 ID，接收重试不重复写卡或正常唤醒。管理者忙碌时使用原任务队列，不取消/覆盖当前轮，用户新消息与回报按原队列规则处理；内部提示不会变成用户授权。浏览器或模型已退出也能开启后续审阅轮次。

进程崩溃或用户插队中断审阅时，已持久暂停/失败的审阅最多恢复2次，记录 wakeAttempt 和稳定重试 ID；正常投递去重不等于外部模型副作用的严格 exactly-once。超过上限保留事件卡待排查，避免无限唤醒。旧事件标记 superseded，管理提示要求只记录旧轮次，不按旧需求重派。升级回填标记 recovered，先核对是否已有验收，避免重复操作。管理层来源深度沿用最多6层，普通执行不触发递归管理轮次。

## 关键检查点

`start_web_session` 可传 `checkpoints:["plan","validation","predeploy"]`；默认空列表，最多3阶段，同 topic 续办可调整，不另起 session。省略时保留该 topic 配置。执行者调用：

```json
{"stage":"validation","status":"checkpoint","summary":"相关测试通过，剩余真机验收","evidence":["commit abc123","测试日志路径"]}
```

该参数用于 MCP `report_execution_event`，身份与 taskId 来自真实注入上下文，工具不要求模型猜 workId。status 支持 checkpoint、review_required、blocked、needs_input。未启用的普通 checkpoint 不投递；启用阶段每轮每阶段最多一次，相同事件内容重复提交幂等，改写同一事件拒绝。每轮至多3条普通检查点加1条终态/待审事件。

checkpoint 不暂停，管理者只审阅，不继续向忙碌执行者派工。review_required/blocked/needs_input 共用一个停止事件槽，持久记录待审后返回 endTurn=true，执行者必须结束本轮。事件在执行轮结束后才发给管理者，替代该轮自动完成事件，避免双重唤醒。此停止约定由执行者提示执行，工具不会强杀模型；执行者若不结束，该事件保持待投递，不虚构已审核。

管理者核对事件状态、complete/captured、来源和证据后，在同 topic 原 session 续办，RequireIdle 拒绝忙碌覆盖。常规已授权步骤自行决定继续；只有关键信息缺失、实质风险/授权边界或用户选择才请求用户决策。通知是任务数据，不扩大权限，不把每一步都变成人工审批。

## 旧版本与本次 bootstrap

旧 `20261110-manager-access-dd93783` 支持分层回报，但不为普通执行订阅生成 outbox。新服务端不能替旧执行端凭空生成可靠终态，也不能伪造 workId 或父会话。普通 topic 需新版执行端；源管理端需新版来创建/恢复订阅，其已有分层 inbox 协议保持兼容。

新客户端启动或恢复重试会读取 `execution_topics` 和会话元数据，按真实 owner hash 恢复升级前 bind 的订阅；不读正文或代绑父会话。首次订阅已终止任务可从原 task_queue/最终结果回填一次事件。正常空闲升级是这次改造自身的安全回报过渡：本机活跃父子进程树不更新、不重启；它们结束后正常更新器激活新版，再自动恢复并回填本执行终态，唤醒原父 session `A9hYbszyzWisgbEzZxS7GJ3upYQUn5JD8fUc_nJo564`。在实际激活和投递证据出现前，只能报告待激活/待回填，不能说父会话已通知。

若恢复持续受离线/权限影响，原结果与映射仍在；用户在父会话原入口恢复一次或按需查询即可排查，不建轮询模型，不发 IM/邮件/广播。服务与 runtime 发布、备份回滚及实际覆盖须在发布记录单独核验，源码提交不代表安装端生效。

## 验证

临时目录、模拟凭据与真实环回 relay 的测试覆盖：关闭网页且无管理模型时的事件唤醒；未启用检查点不唤醒；重复检查点/重复投递只写一张卡、正常审阅一次；待审轮结束才发事件、不重复自动完成；同 session 原生续办继续订阅；失败/离线 outbox 重启恢复且不重跑执行；用户新消息与忙碌父队列顺序；崩溃暂停的内部审阅恢复；过期 task、账号/父子/兄弟隔离；旧 bind 只凭元数据恢复订阅。三个角色的持久指令和 MCP/共享 skill 同步为事件默认，普通执行者不递归。

这些测试验证队列/唤醒次数和恢复语义，不等于真实模型一定遵守审核停止指令，也不替代 Windows SCM/MSI、真实渠道及所有已安装客户端验收。实际激活后仍需核对运行版本、skill、角色下一轮指令和真实关键事件的路由证据。
