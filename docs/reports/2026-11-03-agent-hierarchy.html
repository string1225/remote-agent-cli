Architecture research & implementation proposal

一个 CEO，多个管家。
上下协作，直接追问。

在现有 Go daemon、139 中转、持久会话之上建立分层 Agent：CEO 理解全局，客户端管家调配机器，项目管家维护项目。结果保留来源，用户可以直接与真正的执行者继续沟通。

研究对象：DeepSeek dsh-superagent原型提交：6337fc8三层架构：设计提案本轮代码：报告预览 + 旧端错误诊断

01 / DECISION建议采纳三层结构，把可靠性放在工程层

01

角色长期存在

CEO、客户端管家、项目管家各有稳定身份、工作范围和多个会话。CLI 进程按轮次启动，空闲时不占模型执行槽。

02

事件可靠抵达

派工、结果、人工回复都先持久化，再投递。收到请求、执行完成、向用户送达是三个不同状态，断线后按 ID 去重重试。

03

回复直接到源头

结果卡携带工程生成的回复引用。点“回复执行者”后，经 139 直达原会话，随后把状态同步给上层，无需上层模型再次解释指令。

架构选择：组织关系是一棵树，任务委派关系是有向图，消息返回路径由来源记录决定。跨级回复改变这次消息的投递目标，不改变任务归属、原会话或用户权限。

眼镜和手机默认进入 CEO，也能从结果卡进入项目会话。网页可以直接打开每一层。139 负责身份、路由、目录和显式上传的报告；工作正文、会话、凭证与录音仍由客户端保存。

02 / RESEARCH借鉴 dsh 的机制，保留本项目的边界

dsh-superagent-prototype 是面向单个 GitHub 仓库的研究原型，主会话负责接收与路由，执行会话负责实际工作。它不是现成的跨设备三层系统；这里的 CEO / 客户端 / 项目结构是针对 Remote Agent 的扩展设计。

原型的机制对本库的帮助适配方式
Trigger / Thread / Ticket区分一条来信、持续会话和被授权的工作保留现有 Conversation；增加 WorkItem 作为跨会话任务身份，避免用 Session ID 代替全部业务状态。
Ticket / Assignment 分离重试、迁移执行者后，任务身份仍然稳定WorkItem 长期存在；每次派工生成 Assignment；底层 CLI 一轮仍用现有 taskId。
Effects / Outbox进程退出或网络失败时，消息与执行不丢失在现有 bbolt 事务中写 inbox/outbox，再由 daemon 投递；不引入 SQLite/TypeScript 运行时。
明确归属的追问先给执行者减少每条追问经过主模型的延迟结果引用和入口消息 ID 确定目标。主题相似、文本里的 Session ID 均不能自动获得路由权。
结构化 Report / Attention可靠识别完成、失败、需要人工决定结果带状态、证据、产物和 replyHandle；人工决定复用账号待办，并关联 workItemId。
主会话不阻塞等待CEO 可以同时处理不同人的请求和多个项目为新分层任务提供完成事件唤醒；现有普通父子会话继续保持手动 read/wait 语义。
版本化提示词与授权范围管家行为可追溯，外部文本不能扩大权限会话记录 role/skill/prompt 版本；权限、归属、去重、目标核验由 Go 代码强制实施。

不照搬原型的 GitHub PR 交付流程、每任务 worktree、DSH 特有运行时和“主会话只路由”的全部限制。本仓库继续遵守 main 直接提交与推送规则；CEO 可以回答全局问题，涉及项目细节时再委派。

研究核对了编号文档，并抽查 src/core/intake.ts、src/core/replies.ts 和 src/app/effects.ts；未安装或运行其模型、GitHub、飞书集成。

05 / IDENTITY & WORKSPACE核心 Agent 独立维护，身份与机器位置分开

账号只有一个 CEO 身份；默认主机是它当前的执行位置。CEO 有多个长期会话，不能用一个无限增长的大会话承载全部工作。默认主机离线时网页仍展示缓存和离线状态，不自动在其他机器另建 CEO。

默认主机：~/.remote-agent/
  workspaces/ceo/                 # 独立于任意代码仓库
    AGENTS.md                    # CEO 工作约定
    memory/                      # 用户偏好 / 全局目标 / 摘要
    artifacts/                   # 报告本地原件
  workspaces/client/             # 该客户端管家自己的工作区
  history.db                     # 保留原会话；新增分层与事件桶

项目目录：原工作目录不移动、不强制新建 worktree
  AGENTS.md                      # 原项目规则继续生效
  项目知识目录（明确配置）        # 只存可审计摘要，不默认改动仓库

身份示例（设计字段）
  assistantId: 稳定逻辑身份       # 避免与现有 Agent.ID（客户端 ID）混淆
  scope: account | client | project
  hostClientId / projectId / workspace / provider
  hostEpoch / promptRevision / status

组织关系存为小型注册表；会话仍绑定真实 clientId / projectId。新增 CEO 和客户端管家时使用内部标记的系统项目（例如 scope:account），复用当前执行、历史、附件能力；普通项目列表不显示系统项目。系统项目默认不创建 SaySo、不绑定机器人，也不接受普通项目的删除操作。

迁移需扩展：现有“切换默认主机”只迁移待办，不能据此宣称 CEO 也已迁移。新增 CEO 后必须冻结写入，复制其工作区、会话、原生恢复资料、事件与去重记录，核验后切换 hostEpoch。原机数据保留；目标执行器不兼容时，保留旧会话只读，新会话引用摘要，不能伪造原生 resume。

139 保存账号 → CEO 所在主机、代次和路由元数据；CEO 正文与记忆保存在默认主机。主机切换采用 CAS + fencing epoch，旧主机即使迟到重连也不能继续提交新代次结果。初版不做自动选主。

06 / DELEGATION & REPORTING派工向下，事实向上，回答回到用户入口

接收用户消息

手机 / 眼镜产生稳定 messageId 和入口会话 ID，经账号认证进入 CEO 会话；Web 则进入用户当前选中的层级。

建立 WorkItem 并派工

CEO 确定目标、范围、完成标准、回报策略。事务保存 WorkItem + Assignment + outbox，再经 139 投递；成功接收只显示“已接收”。

客户端 / 项目管家落实

目标核验身份、版本、项目与授权，将工作交给既有会话或新任务会话。沿用同会话队列，不允许上层写入任意 sessionId。

执行者产生结构化报告

Report 保存状态、摘要、证据、产物和叶子会话引用。报告与 outbox 在同一事务提交，完成事件可重试且按 reportId 去重。

上层按需被唤醒

状态事件直接更新任务树；需要整合的完成、失败或人工问题进入上层 inbox。普通进度合并展示，多项同时完成可合并一轮总结。

用户收到有来源的结果

默认返回原入口。CEO 总结可引用多张项目结果卡，每张卡独立提供“回复执行者”，汇总结论本身则回复 CEO。

建议状态模型（各对象分开）
WorkItem:  open → waiting_input / ready / failed / cancelled → closed
Assignment: pending → accepted → running → ended
Task:      复用现有 queued / running / done / failed / cancelled
Delivery:  pending → accepted → delivered  （每步有独立回执）

Report {
  reportId, workItemId, assignmentId, status,
  origin: { clientId, projectId, sessionId, taskId },
  summary, evidence[], artifacts[], question?,
  replyHandle, createdAt, revision
}

task.done 是进程事实；ready 是有验证证据的交付判断。没有最终结果、仍在后台运行、或只有工具输出时，不允许上层生成成功卡片。子任务汇报作为数据进入上层，不能被当成新的用户授权。

避免回声：用户入口的结果投递由 returnRoute 唯一负责；上层的状态同步标记 notifyOnly，不再次发同一用户消息。主动额外通知继续使用现有显式通知能力，不自动广播到其他 IM 私聊或群聊。

07 / DIRECT REPLY跨级回复是确定性投递，不需要再猜一次意图

关键是把“用户看见的消息”与“产生它的执行会话”建立可验证关联。模型只决定报告内容，回复目标由服务端和 daemon 依据结构化数据确定。

CEO 展示项目结果卡reportId + opaque replyHandle
→
用户点击回复执行者显示客户端 / 项目 / 会话目标
↓ 不运行 CEO / 客户端管家模型 ↓
139 核验引用与账号明确目标 · 持久回执 · 去重投递
→
原项目 / 叶子会话排队继续上下文 · 状态同步上层
  1. 生成引用。报告提交时工程生成高熵 replyHandle，绑定 accountId、reportId、目标路由、assignmentRevision、授权范围、有效期和 hostEpoch。上层转述时保留原引用，不让模型重写 ID。139 只存核验所需的元数据，不存报告正文。
  2. 明确回复对象。Web/API 只提交 replyHandle + requestId + prompt；用户可见目标标签。服务端从已认证账号解析目标，拒绝前端任意覆写 clientId/projectId/sessionId。
  3. 直接落队。源端先保存 pending reply receipt，再按 Hash(account, reportId, requestId) 生成稳定投递 ID。目标端核验范围后复用原会话的持久任务队列，并以同一 ID 去重。外部修改文件、机器人等副作用仍要按任务级幂等策略检查，不承诺分布式 exactly-once。
  4. 接收后回执。客户端的 accepted 回执与完成结果分别显示。网络确认丢失时重试相同 ID；同一 ID 携带不同正文返回冲突，不能覆盖已有指令。
  5. 同步上层。CEO / 客户端管家获得“用户直接续办”及后续结果事件，不额外派发同一指令。用户可以一直在该结果线程继续，或显式返回 CEO。
  6. 处理过期与歧义。目标已删除、授权撤销、代次变化、报告被取代时返回明确状态。允许用户查看原上下文并重新选择，绝不静默换会话。多个报告被合并成一段总结时，必须选择具体来源卡，整段总结默认回 CEO。
入口确定目标的工程记录无明确目标时
网页 / 手机结果卡 replyHandle；输入区显示目标标签，发送后保留线程关系进入当前选中的会话，不依据文本关键词跨级。
飞书 / 钉钉平台消息 ID / 引用回复 → reportId 映射，保存在持有机器人凭证的客户端平台无法提供引用时，用可见短码或链接选择；普通来信继续原 IM 会话。
眼镜语音当前选中结果的线程 ID；“回复这条”由 UI 显式附上引用有多个候选时确认对象；没有引用则默认 CEO。

延迟收益：直接回复仍经过 139 网络中转和目标执行器排队，但跳过两层模型路由。示意公式：原路径 = CEO 推理 + 管家推理 + 项目执行；直接路径 = 引用核验 + 项目执行。没有实测数据，不能承诺固定节省秒数。

权限保持：现有普通 send_to_session 只允许直接子会话，继续保留。跨级回复走新的用户来源受限路由，不放宽所有 agent 对所有会话的读写权限；用户新指令属于用户，agent 的观察订阅不构成授权。

08 / CLI & SKILLSCLI、MCP、Skill 共用同一服务实现

客户端间继续使用 Remote Agent 的账号认证与 139 中转，CLI 不直接连接另一台电脑的 shell。当前可通过 remote-agent mcp 使用既有会话工具；下列友好的 CLI 子命令和新协议是建议新增能力。

# 拟新增 CLI（本轮尚未实现）
remote-agent assistants list --json
remote-agent work create --assistant ASSISTANT_ID --input-file task.json --request-id ID
remote-agent work read --id WORK_ID --json
remote-agent work reply --handle HANDLE --input-file reply.txt --request-id ID
remote-agent reports publish --work WORK_ID --input-file report.json

# 已有能力：上传单文件 HTML 后得到下载 / 预览地址（服务端需升级）
remote-agent files upload --path report.html
Skill职责工程配套
remote-agent（现有，扩展）发现设备/项目、查询版本、跨设备任务、报告与回复引用与 MCP 共用类型；JSON 输出、稳定错误码、退出码、请求去重。
ceo-manager（拟新增）全局目标、选择下游、聚合结果、控制通知频率只授账号范围内的派工能力；自动携带真实身份与 returnRoute。
client-steward（拟新增）设备能力、项目路由、负载、维护窗口与故障解释系统变更走白名单 API；不能凭文字绕过更新的忙碌保护。
project-steward（拟新增）项目规则、计划、执行会话、验收证据、知识摘要关联原 projectId；不同入口保留独立 session。
report-author（拟新增，可合并）生成自包含 HTML、上传、记录本地原件与截止时间产物与 workItem/reportId 关联；禁止把凭证写进报告。

Skill 说明“如何使用”；身份、授权、结果投递、过期与去重必须由服务实现。敏感凭据不进参数或输出；CLI 不能接受伪造 callerSessionId。由 daemon 启动的 worker 获得当前轮的受限调用上下文，单独运行的 CLI 只具备设备身份，不能冒充任意用户会话。

建议公共包按职责增加 internal/coordination、internal/protocol 类型与 internal/agent 存储适配，CLI/MCP 仅做参数转换。所有新 RPC 先协商 hierarchyV1 / replyRoutingV1，不按版本名称字符串猜功能。

  • 输入框的回复目标必须可见、可取消；路由状态随草稿按账号和线程隔离保存，切换页面不把指令发到之前的会话。
  • 返回 CEO 只影响后续消息；已接收的下游任务继续执行。归档与删除保留既有恢复规则。

10 / REPORT HOSTING文件上传自然扩展成 HTML 报告交付

本轮将现有临时分享扩展为静态报告阅读：url 保持下载行为；HTML 上传响应新增 previewUrl，即同一随机链接加 ?view=1。报告是单个自包含 HTML，CSS 内嵌，支持电脑、手机及打印。

现在可交付

Agent 本地生成 → CLI 上传 139 → 返回阅读与下载链接 → 原会话交付。报告原件保留在本地，本项目还提交到 docs/reports。

使用边界

知道链接即可阅读。链接在下次北京时间凌晨 4 点到期，下载与预览同时失效。当前能力是临时分享，不是永久报告库。

后续扩展

长期 ReportArtifact 索引、登录可见范围、撤销分享、保留期与版本。需要交互脚本的页面使用无工作台 Cookie 的独立域名和沙箱。

本轮预览采用 CSP 的不透明来源 sandbox，允许内嵌样式与 data 图片，禁止脚本、表单、外部资源、网络和父页面嵌入。不是把任意上传的 HTML 当作工作台代码运行。链接不包含用户工作目录、设备凭据或模型 Token。

显式上传报告属于用户要求的 139 文件托管例外；服务端继续不默认保存所有任务正文与录音。未来长期报告必须明确 retention、owner 和撤销规则，不能借报告索引悄悄集中全部会话。

恢复与并发

  • daemon 重启后重新发送 outbox，目标重放回执；模型进程中断保留上下文与已产生输出，外部操作先检查后续办，不自动重复执行。
  • 同会话只有一个 CLI 轮次，沿用现有队列。管家自动汇报和用户输入都进入持久 inbox；优先级明确，避免汇报洪水饿死用户消息。
  • 任务图设置去重、深度、扇出与循环检查；每次委派必须是更明确的工作范围。汇报链保存 visited / causationId，防止两位管家互相派发。
  • 保持现有后台任务 32 个未完成任务上限，另给全局管家保留有限的控制预算；不让“每项目一个管家”变成同时启动几十个模型。
  • 默认主机断线不创建第二个 CEO。迁移需要新旧主机在线、空闲、备份与校验；旧代次继续只读恢复，不自动合并。
  • 139 短暂离线时本机任务继续，outbox 保留；未送达显示 pending。服务端不承诺在客户端永久丢失后恢复其唯一正文。

数据升级原则

为历史记录增加可选字段和独立 bbolt bucket，旧 kind/source/ID 保留；不批量重命名项目或移动录音。迁移前备份配置、history.db、SaySo 和工作区；验证关联数量、哈希与样本读取后再切换。需要数据库升级的部署成套保存程序、数据库、密钥和配置以便回滚。

12 / DELIVERY PLAN先打通一条可验收的垂直流程

阶段范围完成标准
P0 · 版本与报告基础本轮完成源码：旧待办错误提示、HTML 预览、回归测试、方案。客户端能力/发布同步需要继续落实。旧端不改变默认主机并给明确升级指引；HTML 可读可下载且隔离；线上健康检查通过。
P1 · CEO / 管家身份与 UI注册表、系统项目、独立 workspace、CEO 列表、客户端/项目管家入口刷新/重启身份稳定；原项目和会话 ID 不变；手机默认 CEO；主机离线状态准确。
P2 · 持久派工与汇报WorkItem / Assignment、CLI/MCP 共用接口、inbox/outbox、结构化 Report两台客户端任务经 139 下发并回报；断线/重启不丢、不重复；上层可以继续服务其他任务。
P3 · 跨级回复replyHandle、原会话排队、用户入口回路、上层状态同步用户从 CEO 结果卡直接续办叶子任务，保留原生上下文；两层上级没有路由模型调用；不会双重通知。
P4 · 多入口与报告库飞书/钉钉引用、眼镜选择引用、SaySo 关联、长期报告策略真实渠道消息关联可追溯；不同私聊/群聊隔离；报告权限/期限/撤销得到实际验证。

必须覆盖的验收场景

  1. CEO → Windows 管家 → 项目任务 → HTML 结果；从手机回复结果后直达同一任务会话。
  2. 从网页直接与项目管家发起工作；CEO 能看见授权范围内的状态，且不会重复向用户回话。
  3. 同时在两个项目执行，先完成的一项不会覆盖另一项的回复目标；旧页面慢响应不覆盖新会话。
  4. 发送成功但 ACK 丢失，重复点击与进程重启只创建一次续办任务；同一 requestId 不同内容返回冲突。
  5. 主机/目标离线、旧版本、引用过期、用户停用、设备撤销、项目删除、迁移中、并发人工决定都有明确结果。
  6. 模拟测试使用临时目录与假凭据；真实 Windows Service 生命周期、IM、手机/眼镜和模型端到端单独验收，不以单元测试代替。

建议首个可体验版本只做“一位 CEO → 一个既有项目 → 一张可直接回复的结果卡”，把工程回路跑通后再扩展完整客户端管家、IM 和眼镜，避免一次改变全部入口与存储。

13 / INCIDENT“设为默认主机”为什么报 unknown request type

根因已确认：网页发 PUT /api/default-host，服务端向目标客户端发 todos.call 的 probe，目标旧业务程序不认识请求，进入默认分支返回 unknown request type。这是协议版本差异；不是客户端重新绑定、账号权限或待办正文损坏。

Web 设为默认主机
  → 139 defaultHost()
  → accountRelay(accountTools=true)
  → todos.call { operation: "probe" }
  → 旧客户端：unknown request type

本轮服务端修正：
  “目标客户端版本不支持账号待办（todos.call），
   请先升级该客户端后重试；若检查更新显示已是最新版本，
   需要先发布包含待办协议的新客户端安装包。”

实测本机客户端和 Windows 发布清单都指向 20261102-port-auto / 2026110201，所以单纯点击“检查更新”会显示已是最新。当前会话运行在这个客户端中，强制重启会中断本轮及其他正在执行的任务。

修复边界：清晰报错和保留原默认主机已落实到代码与回归测试；让旧客户端真正支持待办，需要发布包含协议的签名业务版本并在空闲时升级。本执行身份无权读取桌面用户的发布签名目录，不能冒用信任根、生成替代私钥或把本地编译当成已发布。本轮不强制更新正在执行的服务。

后续应把 accountTodosV1 等能力写入握手与更新清单，使网页能在选择前明确显示“不支持，需要升级”。目标 probe 仍保留，用于检查磁盘与存储实际可用；不能只看 UI 开关就宣称就绪。
